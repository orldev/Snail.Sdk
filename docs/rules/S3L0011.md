# S3L0011: Answer in the envelope

A tool of an MCP server answers in the one envelope, `{"ok":true,"data":…}` or `{"ok":false,"error":"…","hint":"…"}`,
written by `ToolAnswer` or `JobAnswer` of `Snail.Sdk.Mcp.Hosting`.

| | |
| --- | --- |
| Category | `Snail` |
| Severity | warning — an error under `TreatWarningsAsErrors`, which every Snail project builds with |
| Analyzer | `OneEnvelope` in `Snail.Sdk.Analyzers` |
| Code fix | none |

## What it reports

A method marked `[McpServerTool]` whose answer is certain not to be the envelope:

| The tool | Reported at | Reported as |
| --- | --- | --- |
| returns nothing — `void`, `Task`, `ValueTask` | the return type | `answers nothing` |
| returns a record, a `JsonNode`, a number, content blocks or any other type, or a task of one | the return type | `answers 'Report'` |
| returns a `CallToolResult` it builds in its `return` with `new` | the `new` | `answers a CallToolResult built by hand` |
| returns a string written in place: a literal, an interpolation, a concatenation, `string.Empty`, `string.Format`, `Concat` or `Join`, a `ToString()`, `JsonSerializer.Serialize`, `JsonNode.ToJsonString` | that expression | `answers plain text` |

The returns are followed through parentheses, `?:`, `??`, a switch expression, `!` and `Task.FromResult` or
`ValueTask.FromResult`. Returns inside a lambda or a local function are not the tool's.

## What it leaves alone

What it cannot see, rather than flag a tool that answers well:

- a `CallToolResult` or a string handed over by a call — `ToolAnswer.Ok(…)`, `JobAnswer.Envelope(report)`, and a method
  of the server's own as well (Snail.MCP.Figma's string tools return `ExecuteAsync(…)`, which writes the envelope);
- a local variable or a field returned, whatever it holds;
- a tool that returns `object`, a type parameter or `dynamic`;
- `Envelope<T>`, the envelope as a type;
- a test's tools, which are doubles: `Snail.Sdk.Tests.globalconfig` turns the rule off in a project of kind `Tests`
  or `Benchmarks`;
- a project that does not reference the MCP SDK.

So a string tool that builds plain text in a helper and returns the helper's answer passes; the rule catches the
answer written where the tool returns it.

## Why

A model reads the shape it was given last. A server whose tools answer in one envelope teaches it one shape — `ok`,
then `data` or `error` and `hint` — and a refusal shaped otherwise is one it misreads as an answer. Every server of the
fleet answers in the envelope ([guidelines](../guidelines.md)); nothing checked it, so a tool that answered plain text
or a record passed the build (finding #52). The one tool the rule found in the fleet when it came, Snail.MCP.Figma's
`csharp_diagnose`, returned its report as `report.ToJsonString(…)`: JSON, but not the envelope.

## How to fix

Answer through `ToolAnswer`:

```csharp
[McpServerTool(Name = "demo_count", ReadOnly = true)]
public CallToolResult Count(string folder) =>
    ToolAnswer.Ok(new JsonObject { ["files"] = Directory.GetFiles(folder).Length });
```

A tool that returns a string returns the envelope's text:

```csharp
return ToolAnswer.OkText(report);
```

A failure is `ToolAnswer.Failed(error, hint, type)` or `FailedText(…)`; a job is `JobAnswer.Envelope(report)`; an
`Answer<T>` is `ToolAnswer.From(answer, AnswerFields.Of)`.

## Suppressing it

Fix the code rather than silence the rule. A server outside the fleet whose answers are text a command, a hook or a
person reads as it is (`.ExplainFailures(options => options.AnswersText = true)`) suppresses the rule for its tools
and says why:

```csharp
[SuppressMessage("Snail", "S3L0011:Answer in the envelope", Justification = "<why these answers are text>")]
```

A `NoWarn` in a project or props file would hide the rule from every new tool too; the
[conformance check](../conformance.md) reports one as migration debt (S3LC0017).
